# CPU 原生编码优化实验

日期：2026-10-20。分支：`feat/cpu-codec-feasibility`。
本轮接续 [调度实验](cpu_codec_scheduling.md)，以 `98d9026` 为对照，
优化 C++ 编码循环。Python 接口、线程池、流水粒度、GPU 编解码器和存储格式均保持原样。
当前原生实现仍只覆盖编码，CPU 解码使用参考实现。

## 结论

本轮将纯编码延迟降低约 **26%**，完整 CPU 路径降低约 **22–25%**，
每个编码器仅增加 **768 字节**工作区。64-slot、16 线程、每组 8 slot 的流水路径
从 **189.307 ms** 降至 **142.676 ms**，延迟减少 **24.63%**；
p95 从 **192.365 ms** 降至 **143.144 ms**，原始字节吞吐从约 **5.67 GB/s**
提高到 **7.53 GB/s**。

同次优化版运行的 GPU 完整路径为 **18.227 ms**，CPU 仍慢 **7.83×**。
因此保留这项局部优化，但没有据此改变“暂不整体迁移在线编解码到 CPU”的判断。
收益适用于本次编码实现、输入和硬件，不能外推为 CPU 解码或 TTFT 改善。

## 实现与正确性约束

首轮代码逐标量更新 3-bit 位流，并在同一循环内判断转义类别和 tile 结束位置。
本轮将这些工作拆为 tile 内分类、顺序压紧转义符号、批量输出：

- 每个实例复用三个 256 字节数组，分别容纳主符号、次级符号和原始高字节。
- 转义候选先写入临时数组，再按谓词推进有效长度；未接受的候选被后续值覆盖。
  写入前的有效长度不超过当前 tile 内下标，因此即使最后一个符号不是转义也不会越界。
  这种写法只用于 tile 工作区，不用于精确长度的输出流。
- 每八个 3-bit 符号使用整数移位和掩码合成三字节，主符号和次级符号共用该写入逻辑。
  次级流跨 tile 保留不足一字节的状态；仅写有效的三个字节及最终短尾。
- tile 前缀在 tile 结束后写入，标量循环不再逐次判断边界。

第一遍计数、整槽长度判断和 RAW 回退没有改变。没有新增 ISA 要求、内部线程、
稳态原生分配或跨 slot 可变状态；调用方仍需保证输入稳定且与输出不重叠。
注释说明了位合并过程、候选写入的界限及跨 tile 的 carry，避免依赖未经说明的对齐或字节序假设。

## 实验协议

重新采集同一份 BF16 Meta-Llama-3.1-8B 固定文本 KV：8192 token、64 个完整 slot，
每 slot 128 token、32 层、8 KV heads、head_dim 128，16 MiB，总计 1 GiB。
采集 manifest 与[首轮记录](data/cpu_codec_feasibility/capture.json)完全相同，
原始数据 SHA-256 仍为
`afab4b39d6b387db8d97311d89603de57b62897f519e506f95e2d7b499439208`。

优化前后使用独立共享库，均为 GCC 12.3、
`-O3 -DNDEBUG -std=c++17 -Wall -Wextra -Werror -fPIC -shared`，
没有 `-march=native`。H800（GPU 4）启动前空闲，CPU 和内存绑定 NUMA 1；
CPU 为双路 Xeon Platinum 8558。其他 GPU／主机负载未隔离；开发筛选在 NUMA 0 进行。
Torch 2.13.0+cu129、TileLang 0.1.12、Transformers 5.19.0、NumPy 2.2.6。

本轮重新运行基线，随后运行优化版；两者都使用相同输入、码表和 benchmark 源码：

```bash
numactl --cpunodebind="$NUMA_NODE" --membind="$NUMA_NODE" \
  python -m benchmarks.compression.bench_cpu_codec \
  --capture "$RUN_DIR/capture" --output "$RUN_DIR/results.json" \
  --threads 8 16 --batch-sizes 16 64 \
  --pipeline-chunk-slots 8 --profile-iterations 10 \
  --warmups 5 --iterations 30 --rounds 3
```

分别设置 `DASER_CPU_CODEC_LIBRARY` 选择优化前后共享库，并使用不同结果文件。
完整编译和采集说明见 [benchmark README](../../benchmarks/compression/README.md)。
每个版本 14 组、1260 个稳态样本和 120 次独立诊断；合计 **28 组、2520 个稳态样本、
240 次诊断**。下文 median/p95 使用各组全部 90 个样本，不与历史运行或开发筛选混算。

`cpu_encode` 从已驻留主机 canonical 数据开始；
`cpu_full` 包含整批原始 D2H、同步、CPU 布局转换与编码；
`cpu_full_pipelined` 按 8-slot 分组重叠 D2H 和 CPU 工作。
`gpu_full` 包含现有 GPU 编码、紧密排列、元数据处理和仅有效记录的 D2H。
全部路径在主机结果可用处停止，编译、采集、初始 H2D、缓冲分配和验证哈希均不计时。
没有测量 NVMe、IPC、并发推理、TTFT 或在线服务接入。

GPU 代码没有改动，两次测量的中位数差异小于 1%。CPU 改善明显大于此次 GPU 对照波动，
但这是顺序执行的固定语料实验，不是随机交错的服务端因果实验。
16-slot、16 线程下，流水的中位数略低于整批路径，但 p95 **42.317 ms** 高于整批的
**40.580 ms**；对小批次不能仅按中位数选择流水配置。

独立诊断中，64-slot、16 线程流水的 D2H 提交／等待从 **19.964 ms** 到 **19.915 ms**，
布局 worker 耗时之和从 **175.827 ms** 到 **174.977 ms**，
编码 worker 耗时之和从 **2771.091 ms** 降至 **2043.920 ms**。
这些是各阶段跨 10 次诊断的中位数，worker 耗时是并行墙钟区间之和，不能相加作为完整路径延迟。
它们支持“收益来自编码循环”的解释；没有进行硬件性能计数器归因。

## 压缩、内存与正确性

两种实现的 64-slot 校验记录完全一致，包括存储模式、长度和有效记录摘要。
CPU/GPU 均存储 **794,304,512 字节**，压缩率 **1.3518×**，
真实语料 **0/64 RAW 回退**。整槽回退、格式和占位内容哈希约定保持原样；
参考解码仍默认检查内容哈希，实验显式跳过占位哈希后逐字节比较。

原生工作区每实例从 **22,336** 增至 **23,104 字节**。
16 个实例合计从 **357,376** 增至 **369,664 字节**，增加 **12 KiB**。
64-slot、16 线程完整路径的其余容量仍为 1 GiB 输出、1 GiB pinned 输入、
256 MiB canonical 缓冲，另有共享的 1 GiB 主机语料和 1 GiB GPU 输入。
两次主进程 RSS 范围都约为 2.30–4.29 GiB；RSS 包含缓存，不用来归因这 12 KiB 的变化。

- 基线与优化版各自完成 64-slot 的 CPU→参考、CPU→GPU、GPU→GPU 逐字节恢复和布局验证。
- 新增 8 组公开接口测试，覆盖次级流所有起始位偏移、tile 尾块、密集／稀疏转义、
  非对齐输入输出和完整记录字节比较；保留已有 RAW 回退、特殊 BF16、混合批次及缓冲复用测试。
- **24 项专项测试在 UBSan 下通过**；优化版 release 库的默认回归为
  **579 passed、136 deselected**。Ruff lint/format 和 `git diff --check` 通过。
- 两个版本全部 **240 次诊断时间线**均满足复制完成后处理对应 slot、所有任务完成后返回的约束。

## 后续判断

当前改善来自原生实现，调度收益可以在其上继续保留。但 16-slot 和 64-slot 的最佳 CPU
完整路径仍分别慢于 GPU **8.19×、7.83×**，没有证明 CPU 编码能改善并发推理端点。
后续若考虑后台 CPU 编码，应以有界队列和内存预算下的实际写入速率、TTFT、TPOT/ITL
及生成吞吐为判断依据；当前约 7.53 GB/s 的批处理吞吐不能直接用作服务容量承诺。
