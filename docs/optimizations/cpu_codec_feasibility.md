# CPU 编码可行性实验

日期：2026-10-20。基线：`master@5184597`。分支：`feat/cpu-codec-feasibility`。

已有 Python/NumPy CPU reference codec 及 CPU→GPU 解码测试，因此格式互操作性已有依据。
本轮新增的是显式编译的 C++ CPU 编码器、可复用工作区，以及包含原始 KV 搬运与布局转换的性能测量。
同时核对了最新远端 `research/lossless-kv-e2e@2d64852`，并复跑其现有 CPU codec／GPU 兼容性测试：17 项通过。

## 结论

新增原生编码器在全部真实输入与边界测试上无损恢复。当前实现的 CPU 完整路径明显慢于 GPU；
8 线程、16-slot 批次仍慢 18.7 倍，不建议据此直接接入要求低延迟的同步写入路径。
这个结论限于本次通用 C++ 实现和空闲 GPU 条件，不是 CPU 编码性能上限；没有测量并发推理争用或 TTFT。

| 批大小 | CPU 实际线程 | CPU 完整 median / p95 (ms) | GPU 完整 median / p95 (ms) | CPU / GPU median |
|---:|---:|---:|---:|---:|
| 1 | 1 | 45.044 / 45.558 | 0.766 / 0.789 | 58.8× |
| 4 | 4 | 46.257 / 46.579 | 1.611 / 1.626 | 28.7× |
| 16 | 8 | 95.759 / 96.488 | 5.130 / 5.154 | 18.7× |

上表固定请求 8 线程，批大小不足时限制实际并行度。全部配置如下，未按最快单次结果筛选。

## 输入与计时边界

- 本地 BF16 Meta-Llama-3.1-8B，固定文本重复至 8192 token，采集 post-RoPE K/V。
- 64 个完整 128-token slot；32 层、8 KV heads、head_dim 128；每 slot 16 MiB，总计 1 GiB。
- 两方使用相同输入和默认码表，256-scalar tile，4 KiB 对齐；没有校准码表。
- H800（GPU 4），CPU 为双路 Xeon Platinum 8558。进程 CPU 和内存绑定到 GPU 所在 NUMA 1；线程允许在该节点内调度。
- GPU 4 在启动前空闲；其他 GPU 有独立负载，这不是整机隔离实验。仓库回归测试使用 NUMA 0／GPU 1。
- GCC 12.3，`-O3 -DNDEBUG -std=c++17`；无手写 SIMD 或 `-march=native`。Torch 2.13.0+cu129、TileLang 0.1.12、Transformers 5.19.0、NumPy 2.2.6。
- 每组每轮预热 5 次、测量 30 次，共 3 轮。表中 median/p95 来自该组全部 90 个样本；吞吐按原始字节计算，单位十进制 GB/s。

`cpu_encode` 从已驻留的主机 canonical 数据开始；`cpu_full` 从 GPU 的物理
`[block, layer, token, head, K/V, dim]` 数据开始，包含 pinned D2H、同步、CPU 布局转换、
固定线程池分派和原生编码。CPU 输出保留各 slot 的独立预分配缓冲。
`gpu_full` 包含现有 GPU 编码、紧密排列、元数据处理和同步，只将实际有效记录 D2H，等待复制完成。
两条路径都在主机结果可用处停止；不包含 NVMe 写盘、IPC、推理或跨批流水重叠。

编译、采集、初始 H2D、缓冲分配、参考解码和内容校验不计入稳态时间。
参考解码使用 4 个 spawn 子进程，全部退出后才开始测量；编码使用固定线程池，每个工作线程独占编码器。

16-slot 时 CPU 编码从单线程 693.878 ms 降到 8 线程 87.456 ms，接近 8× 提速；
计入搬运和布局转换后为 95.759 ms，比编码本身增加约 8.3 ms。GPU 完整路径为 5.130 ms，

主要瓶颈仍是当前 CPU 位流编码本身。上述差值是独立测量组中位数之差，不是分阶段计时。

## 压缩、回退与内存

CPU 和 GPU 的存储长度均为 794,304,512 字节，原始／存储压缩率 **1.3518×**，节省约 **26.0%**。
真实语料两方都是 0/64 RAW 回退；64 个 slot 的有效记录正文摘要也一致。此处不比较 GPU 未定义的尾部对齐填充。
CPU 按整槽实际长度回退；GPU 还受逐平面转义容量限制。当前语料未触发这种差异，不能推出其他输入的回退率相同。

每个编码器的原生工作区为 **22,336 字节（21.8125 KiB）**，含对象、查找表、逐平面计数和模板头部。
不含 Python 对象、分配器元数据及输入输出缓冲。8 个实例合计 178,688 字节。

下表使用请求 8 线程配置，容量单位 MiB；另有共享的 1 GiB 主机语料和 1 GiB GPU 输入。

| 批大小 | CPU 输出 | CPU pinned 原始输入 | CPU 布局缓冲 | GPU 路径 pinned 输出 | GPU 输出 staging | GPU packer 工作区 |
|---:|---:|---:|---:|---:|---:|---:|
| 1 | 16.00 | 16.00 | 16.00 | 16.00 | 16.00 | 3.27 |
| 4 | 64.00 | 64.00 | 64.00 | 64.00 | 64.00 | 13.03 |
| 16 | 256.00 | 256.00 | 128.00 | 256.00 | 256.00 | 52.06 |

CPU 编码单独路径只需其输出缓冲和原生工作区；完整路径增加 pinned 原始输入及每线程 canonical 缓冲。
测量时主进程 RSS 约 2.07–2.50 GiB，进程峰值约 3.49 GiB，峰值包含前面的校验阶段。
JSON 逐组记录 RSS、峰值、Torch GPU allocated/reserved；这些数值包含缓存，不能用作独立的 codec 内存归因。
参考校验子进程内存不计入主进程 RSS；编解码稳态阶段没有这些子进程，也没有驻留模型权重。

## 正确性与实现边界

- 64 个真实 slot：CPU→参考、CPU→GPU、GPU→GPU 逐字节恢复均通过，CPU 布局转换也与 canonical 数据一致。
- 13 项最终边界／GPU 兼容测试在 UBSan 下通过，覆盖转义类别、entry 14、特殊 BF16 位模式、全部 65536 种 BF16 位模式、tile 尾块、整槽回退、单平面集中转义、缓冲复用及混合批次。
- 默认非 integration／非 slow 测试：571 passed、133 deselected；Ruff lint 和 format 检查通过。
- 最新研究分支原有 CPU reference／GPU 兼容性测试另外复跑：17 passed。
- 原生实现不依赖 Torch/pybind11 构建，导入 Python 封装不会导入 Torch；C 调用释放 GIL，原生稳态编码不分配堆内存。
- 占位内容哈希与 GPU 一致，为 `01` 加 31 个零字节；码表哈希正常保存。参考解码器仍默认校验内容哈希，仅实验显式跳过并进行字节比较。
- 复用 master 的单页头部，最多 41 层；本轮不移植研究分支的多页头部扩展，不处理部分有效 token，也不接入在线服务。

首轮实验的 GPU 输出摘要曾因包含未定义的尾部填充而失败；修正摘要范围后重新运行了全部 27 组。
本文仅使用最终完整运行。一次隐藏 GPU 的默认测试也暴露了已有 CuPy pinned-memory 测试对可见 GPU 的依赖；
在可见的独立 GPU 上重跑后全部通过，没有为此修改传输层。
