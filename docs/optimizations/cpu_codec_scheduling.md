# CPU codec 调度扩展实验

日期：2026-10-20。分支：`feat/cpu-codec-feasibility`，基于 `master@5184597`。
本轮接续 [CPU 编码可行性实验](cpu_codec_feasibility.md)，保持原生 C++ 编码器、
码表和 GPU 编解码器不变，比较更多 CPU 工作线程与 D2H／CPU 编码分组流水。
这些改动只在离线 benchmark 中实现，没有接入服务写入端。

后续的 [CPU 原生编码优化实验](cpu_codec_native_optimization.md) 在相同接口和调度下
改进了 C++ 位流打包；本文保留调度实验完成时的原始结果。

## 结论

增加线程数的收益明显，分组流水在较大批次中有额外收益，但仍未消除与 GPU 的差距。

- 8→16 线程：16-slot、64-slot 的纯编码分别提速 **1.97×、1.99×**；
  完整路径分别提速 **1.85×、1.86×**。
- 16 线程、64-slot：每 8 个 slot 一组的流水将完整路径从 **206.248 ms**
  降至 **189.177 ms**，延迟减少 **8.28%**；p95 从 **209.842 ms**
  降至 **190.154 ms**。相对 8 线程整批复制的 383.729 ms，合计减少 **50.70%**。
- 16 线程、16-slot：同样流水只将 **51.814 ms** 降至 **51.359 ms**，
  减少 **0.88%**，不足以认定小批次有稳定收益。
- 同次实验的 GPU 完整路径为 **4.919 ms / 19.297 ms**（16-slot / 64-slot）。
  对应最快 CPU 完整路径仍慢 **10.44× / 9.80×**。

因此，后续 CPU 实验可优先采用固定 16 线程池，并在较大批次尝试每组 8 个 slot；
不建议仅凭这次调度改进接入低延迟同步写入路径。此配置只是当前测量范围内的选择，
不代表最优线程数或最优分组大小。更高线程数、原生编码算法优化及推理期间的 GPU 争用仍需另测。
本轮没有测量 TTFT，也没有实现动态迁移。

## 测量边界与实现

重新从本地 BF16 Meta-Llama-3.1-8B 采集固定文本的 8192 token，形成 64 个完整 slot。
每 slot 为 128 token、32 层、8 KV heads、head_dim 128，共 16 MiB；总计 1 GiB。
新采集 manifest 与首轮保存的 [采集参数](data/cpu_codec_feasibility/capture.json) 完全相同，
包括 token IDs、模型配置与原始数据 SHA-256：
`afab4b39d6b387db8d97311d89603de57b62897f519e506f95e2d7b499439208`。

启动前重新检查 H800（GPU 4）为空闲，CPU 和内存绑定到同一 NUMA 1；
CPU 为双路 Xeon Platinum 8558，每路 48 个物理核心。线程允许在 NUMA 节点内调度，
没有逐线程绑核。其他 GPU 存在独立负载，整机未隔离。
默认回归测试的最终重跑在性能矩阵结束后进行，使用 NUMA 0／GPU 1。
软件为 GCC 12.3、Torch 2.13.0+cu129、TileLang 0.1.12、Transformers 5.19.0、NumPy 2.2.6。
原生编译参数仍为 `-O3 -DNDEBUG -std=c++17 -Wall -Wextra -Werror -fPIC -shared`。

| 路径 | 计时范围 |
|---|---|
| `cpu_encode` | 已驻留主机 canonical 输入 → 固定线程池编码 → 主机输出可用 |
| `cpu_full` | GPU 物理布局输入 → 整批 pinned D2H 与同步 → CPU 布局转换与编码 → 主机输出可用 |
| `cpu_full_pipelined` | GPU 物理布局输入 → 分组 D2H 与同步，并与先前分组的 CPU 布局转换／编码重叠 → 全批输出可用 |
| `gpu_full` | 现有 GPU 编码 → 紧密排列与元数据整理 → 有效记录 D2H 与同步 → 主机输出可用 |

CPU 线程池固定为 8 或 16 个 worker，每个 worker 独占编码器及 canonical 布局缓冲；
没有嵌套线程池。分组流水在整批 pinned 输入中使用互不重叠的切片：
主线程复制并等待一组完成，提交该组 CPU 任务，再复制下一组。
每次调用等待全部任务结束，发生异常时也排空已提交任务，随后才允许复用输入输出。
因此同批大小、同线程数下，流水不增加输入输出缓冲容量；没有跨批次流水。
复制与完成等待显式使用同一个 CUDA stream，不依赖调用方之后选择的 current stream。

矩阵为线程数 8/16、批大小 16/64、分组大小 4/8/16；分组不小于批大小时跳过重复项。
共 **20 组、1800 个稳态样本**，每组每轮预热 5 次、测量 30 次，共 3 轮。
另有每个 CPU 配置 10 次诊断，共 **180 次**，不混入性能样本。
下表 median/p95 均来自各组全部 90 个稳态样本；吞吐按原始字节计算，单位十进制 GB/s。
编译、采集、初始 H2D、缓冲分配和内容哈希不计入稳态区间。
各配置按固定顺序执行，没有随机交错；小于 1% 的差异不应解释为普遍收益。

## 分阶段诊断

以下均为 16 线程配置，取各组 10 次独立诊断调用的阶段中位数，单位 ms。
诊断包含时钟记录，逐调用的额外校验在计时外；调用墙钟值与稳态样本略有差异，
不能用于替换上表延迟。

| 批大小 | 路径／分组 | 诊断墙钟 | D2H 提交与等待 | CPU 工作跨度 | 布局 worker 耗时之和 | 编码 worker 耗时之和 |
|---:|---|---:|---:|---:|---:|---:|
| 16 | 整批 | 53.529 | 4.969 | 48.367 | 64.607 | 694.463 |
| 16 | 流水 4 | 53.308 | 5.101 | 51.803 | 62.121 | 697.762 |
| 16 | 流水 8 | 53.611 | 5.016 | 50.881 | 66.178 | 699.105 |
| 64 | 整批 | 208.323 | 19.698 | 188.036 | 188.214 | 2779.408 |
| 64 | 流水 4 | 194.374 | 20.945 | 192.726 | 172.683 | 2779.216 |
| 64 | 流水 8 | 191.023 | 19.973 | 188.114 | 176.141 | 2774.566 |
| 64 | 流水 16 | 194.243 | 20.257 | 188.871 | 184.265 | 2776.159 |

“CPU 工作跨度”是首个任务开始到最后一个任务结束；worker 耗时之和则累加并行任务的墙钟区间，
包含线程被操作系统暂停的时间，并非实际 CPU cycles。这些量彼此重叠，不能相加当成完整延迟。
原始 JSON 还保存每个 slot 的排队时间及每段复制的起止时间。

64-slot 流水 8 的 D2H 累计约 19.97 ms，CPU 工作跨度约 188.11 ms；
按照复制区间与所有 CPU 任务区间并集的交集计算，每次调用重叠时间的中位数约 **17.29 ms**。
这支持“流水主要隐藏了搬运等待”的解释，与稳态完整路径减少约 17.07 ms 相符。
编码 worker 耗时之和基本不变，流水没有加速原生编码本身。

16-slot、16 线程只有一轮 slot 任务；分组越晚到达，最后几个任务也越晚开始。
从时间线看，复制与 CPU 已有重叠，但不足以明显缩短最后一个任务的完成时间。
64-slot 有多轮任务，后续复制可被已有编码任务覆盖。
这是对当前时间线的解释，不是对其他批大小、CPU 负载或码表的性能保证。

## 压缩与内存

CPU/GPU 均存储 **794,304,512 字节**，原始／存储压缩率 **1.3518×**，
节省约 26.0%，真实语料都是 **0/64 RAW 回退**。流水保持相同码表、格式与输出。
CPU 的整槽长度回退与 GPU 的逐平面容量限制仍有区别；本次输入未触发差异。

原生工作区每实例 **22,336 字节**，8/16 个实例分别为 **178,688 / 357,376 字节**。
下表为完整路径缓冲容量，单位 MiB；不含共享的 1 GiB 主机语料、1 GiB GPU 输入、
Python 对象及分配器元数据。CPU 整批路径与所有流水配置的对应容量完全相同。

| 批大小 | CPU 线程 | CPU 输出 | CPU pinned 输入 | CPU canonical 工作区 | GPU pinned 输出 | GPU 输出 staging | GPU packer 工作区 |
|---:|---:|---:|---:|---:|---:|---:|---:|
| 16 | 8 | 256 | 256 | 128 | 256 | 256 | 52.06 |
| 16 | 16 | 256 | 256 | 256 | 256 | 256 | 52.06 |
| 64 | 8 | 1024 | 1024 | 128 | 1024 | 1024 | 208.17 |
| 64 | 16 | 1024 | 1024 | 256 | 1024 | 1024 | 208.17 |

CPU 与 GPU 列表示各自路径的独立分配，不能相加作为同一运行配置。
线程数 8→16 会增加 128 MiB canonical 缓冲，CPU 纯编码路径不需要该布局缓冲或 pinned 输入。
本轮主进程 RSS 约 2.30–4.29 GiB，峰值约 4.30 GiB，包含解释器、校验及缓存；
逐组 RSS、GPU allocated/reserved 在 JSON 中保留，不作为 codec 独立内存占用。
参考解码子进程在稳态测量前已退出。

## 验证与复现

- 64 个真实 slot 的 CPU→参考、CPU→GPU、GPU→GPU 字节比较和布局转换检查全部通过。
  每个稳态轮次结束后检查该轮最后一批有效记录摘要；每次诊断调用逐个核对 mode、长度和摘要，
  所有哈希均在计时区间外。
- CPU codec 专项测试 **16 passed**，包含新增的整批／1-slot／3-slot 分组测试：
  覆盖混合 RAW 与压缩、tile 尾块、最后一个不满分组、输出顺序、重复调用及不同调用方 CUDA stream。
  原有边界测试继续覆盖转义类别、特殊 BF16 位模式及缓冲约束。
- 全部 **180 次诊断时间线**满足复制完成后才开始对应 CPU 任务、任务全部结束后调用才返回。
- 默认非 integration／非 slow 回归 **571 passed、136 deselected**；
  Ruff lint、format 和 `git diff --check` 通过。
